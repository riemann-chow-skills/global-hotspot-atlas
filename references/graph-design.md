# 实体关系建模方法论

图谱好不好看，90% 取决于 `entities` 和 `relations` 怎么建，而不是渲染器。这份文档解决三个最常见的问题：孤点、散团、全灰边。

## 一、先想清楚"这张图要回答什么"

一张好图回答一个具体问题。先在心里定一句话，再开始建实体。

| 问题 | 该保留的实体 | 该丢弃的实体 |
|---|---|---|
| 谁在推动这件事？ | 决策者、机构、国家 | 评论员、围观企业 |
| 冲突卡在哪？ | 谈判方、调解方、卡点议题 | 历史人物、无关第三方 |
| 影响会传导到哪？ | 上游事件、下游市场/供应链 | 泛泛的"国际社会" |

默认取第一个问题。用户若说"我想看对市场的影响"，改取第三个。

## 二、实体数量的甜区

- **15–30 个**：图上每个节点都认得出，连线清晰。
- 少于 10 个：图会稀疏得像流程线，失去"网络"的感觉。
- 多于 40 个：标签互相遮挡，需要放大才能看清，不如减少。

一个实用判据：**如果一个实体只在一条事件里出现一次，且不是关键人物，就不要收**。

## 三、制造"骨架实体"

图谱会连成一片还是碎成几块，取决于有没有**跨事件的共享实体**。开建之前先找出 4–8 个必然横跨多条事件的"骨架实体"，通常是：

- 大国：美国、中国、俄罗斯、欧盟
- 国际组织：联合国、北约、世贸组织、OPEC+
- 议题：能源安全、供应链、AI 监管、气候融资
- 关键地点：霍尔木兹海峡、红海、台湾海峡

先把这些接上，图自然成形；再补具体人物和事件细节。

**反例**（每块互不相连）：

```
evt_1 加沙谈判 ← 以色列、内塔尼亚胡
evt_2 红海航运 ← 马士基、曼德海峡
evt_3 美联储   ← 鲍威尔、美债
```

**正例**（通过共享实体串起来）：

```
evt_1 加沙谈判 ← 以色列、内塔尼亚胡、联合国、能源安全
evt_2 红海航运 ← 曼德海峡、能源安全、欧盟、供应链
evt_3 美联储   ← 鲍威尔、美国、能源安全（油价→通胀）
```

现在「能源安全」和「美国」成了枢纽，三块拼成一张网。

## 四、关系方向：从"具体"指向"抽象"

统一按这个方向画，图会自然形成由内向外扩散的结构，而不是乱麻：

```
人物 ──→ 组织/国家 ──→ 事件 ──→ 议题 ──→ 地点
```

也就是说：

- 人物 → 国家/组织：`participate`（担任、代表）
- 国家/组织 → 事件：`participate` / `stance` / `sanction` / `cooperate`
- 事件 → 议题：`cause`（引发某议题）或 `related`
- 事件/实体 → 地点：`located`

反过来画（议题 → 人物）会让布局变乱，尽量避免。

## 五、关系类型的配比

一条全是 `related` 的图，视觉上就是一片灰线，毫无信息量。健康的配比大致是：

| type | 占比 | 说明 |
|---|---|---|
| `participate` | 35–45% | 主干，撑起结构 |
| `stance` | 20–25% | 让图有"态度"层次 |
| `cooperate` | 10–15% | 绿色，提供对比 |
| `sanction` | 5–10% | 红色，冲突焦点 |
| `cause` | 5–10% | 紫色，体现传导 |
| `located` | 5–10% | 把地点挂上去 |
| `related` | ≤ 10% | 兜底，越少越好 |

写关系时问自己一句："这两者之间，到底是参与、表态、合作，还是对抗？"——想清楚再落 `type`，不要图省事全写 `related`。

## 六、weight 怎么给

`weight` 只影响连线粗细，用来表达关系强度：

- `1.0`：普通提及
- `1.3–1.5`：明确关联（某国是该事件主要当事方）
- `1.6–2.0`：核心关系（发动方、主导方、直接因果）

不要所有边都给 1.5——那样粗细就没有意义了。

## 七、自检清单

提交前逐条过一遍：

- [ ] 每个实体至少有一条边（`build.mjs` 的警告里会点名孤点）
- [ ] 至少 4 个实体出现在 2 条以上事件里（跨事件枢纽）
- [ ] `related` 占比不超过 10%
- [ ] 没有两个实体指向同一角色（比如同时有「以色列」和「以方」）
- [ ] 人物实体的 `desc` 写清了身份（"以色列总理"而不是"政治人物"）
- [ ] 事件节点之间的直接连线不超过 5 条（事件之间主要靠共享实体连接，直接连多了会显得乱）

## 八、一个可复用的建模顺序

1. 列出 12–16 条事件，每条标出 2–4 个 `actors`（先只写名字，不写 id）
2. 把所有名字去重，合并同义项（"以方"→"以色列"）
3. 按"是否跨事件出现"筛一遍，删掉只出现一次的边缘角色
4. 给留下的实体分配 id 和 type
5. 先画骨架实体到事件的边，再补实体之间的边
6. 最后给每条边定 type 和 weight
7. 跑 `node scripts/build.mjs --data atlas.json --check`，按警告修补
